# Оснастка-Маркет — CRM/ERP для металообробного підприємства
# (токарна, фрезерна та універсальна обробка) на власному парку обладнання

## Чесний статус проєкту

Це не демо-макет — усі описані нижче захисти реально реалізовані в коді
й покриті автоматизованими тестами (`test_app.py`, 17 тестів, усі
проходять). Але це і не заводський продукт зі штатом DevOps — нижче
чітко розділено, що зроблено, а що залежить від вашої інфраструктури
(реальний домен, сертифікат, сервер), яку я не можу протестувати
за вас.

### Зроблено і перевірено тестами
- CSRF-захист усіх форм
- Захист від перебору паролів (блокування на 5 хв після 5 невдалих спроб)
- Рольовий доступ на рівні сервера (не лише приховування кнопок)
- Серверна валідація форм (від'ємні суми, текст замість чисел, порожні
  обов'язкові поля — все дає зрозумілу помилку, а не крах сервера)
- Захист складу від списання в мінус
- Коректна мультивалютна аналітика (конвертація в грн перед підсумовуванням)
- Безпечна конкурентність SQLite (WAL-режим, чекає замість миттєвого збою)
- Автоматична міграція схеми БД (оновлення коду не ламає вже існуючу базу)
- Резервне копіювання через офіційний backup API SQLite (не б'ється при
  одночасному записі)
- Обробники помилок 404/500 без витоку деталей коду користувачу
- Логування помилок у файл (`logs/crm.log`)
- Production WSGI-запуск через gunicorn (не вбудований dev-сервер Flask)
- Захист від перебору паролів через БД (не пам'ять процесу — коректно
  працює навіть при кількох gunicorn-воркерах, перевірено на реальному
  gunicorn з 3 воркерами)
- Самообслуговування: кожен користувач може змінити власний пароль
  («Мій профіль» в бічній панелі)
- Пагінація списку клієнтів (по 50 на сторінку — не гальмує при рості бази)

### Досі залежить від вашого середовища (я не можу зробити це за вас)
- **HTTPS-сертифікат** — потребує реального домену. Конфіг nginx під
  Let's Encrypt додано (`deploy/nginx.conf.example`), лишається
  прив'язати ваш домен і виконати `certbot`.
- **Регулярний бекап за розкладом** — кнопка й функція є, лишається
  додати рядок у `cron` (приклад у розділі нижче).
- **Тест Haas-адаптерів на реальному верстаті** — код відповідає
  документації Haas, але жоден верстат тут фізично не підключений.
- **Навантажувальне тестування** з десятками реальних одночасних
  користувачів — SQLite+WAL тримає невеликий/середній офіс (реально
  перевірено на конкурентних запитах), але для 50+ одночасних
  користувачів варто перейти на PostgreSQL.

## Встановлення

```bash
python3 -m venv venv
source venv/bin/activate        # Windows: venv\Scripts\activate
pip install -r requirements.txt
```

## Запуск для розробки/невеликого офісу (1 ПК, локальна мережа)

```bash
export CRM_SECRET_KEY="$(python3 -c 'import secrets; print(secrets.token_hex(32))')"
python app.py
```

За замовчуванням слухає тільки `127.0.0.1` (доступ лише з цього ПК).
Щоб дати доступ іншим ПК у цеховій мережі:

```bash
export CRM_HOST=0.0.0.0
python app.py
```

При першому запуску автоматично створюється `crm.db` із демо-даними.
Щоб почати з чистої бази — видаліть `crm.db` (нові запуски з уже
існуючою базою безпечні — схема мігрує автоматично, дані не губляться).

## Запуск у бою (продакшн)

Вбудований сервер Flask (`python app.py`) — інструмент розробника,
не для постійної роботи з кількома користувачами. У бою:

```bash
export CRM_SECRET_KEY="$(python3 -c 'import secrets; print(secrets.token_hex(32))')"
gunicorn --workers 3 --bind 127.0.0.1:5000 --access-logfile logs/access.log wsgi:app
```

Далі — nginx перед gunicorn для HTTPS (`deploy/nginx.conf.example`) і
systemd для автозапуску при перезавантаженні сервера
(`deploy/osnastka-market.service`). На Windows замість gunicorn — `waitress`
(`pip install waitress; waitress-serve --host=0.0.0.0 --port=5000 wsgi:app`).

## Автоматичне резервне копіювання (cron)

```bash
# Щоночі о 2:00, зберігає останні 30 копій автоматично
0 2 * * * cd /шлях/до/crm && /шлях/до/venv/bin/python3 -c "import app; app.backup_database()"
```

Копію також можна створити вручну кнопкою на сторінці «Налаштування».

## Автоматизовані тести

```bash
pip install pytest
pytest test_app.py -v
```

30 тестів покривають: логін і блокування перебору паролів (у т.ч.
підтверджено, що воно коректно працює через БД, а не пам'ять процесу —
критично для gunicorn з кількома worker'ами), CSRF,
рольовий доступ, валідацію форм, автоматичне створення виробничого
замовлення при передоплаті, коректність алгоритму планування
(послідовність операцій), захист складу від від'ємного залишку,
мультивалютну аналітику, і те, що стара база даних переживає
оновлення коду. Запускайте цей набір після будь-яких змін у `app.py`,
щоб одразу побачити, чи щось зламалось.

## Установчий .exe для Windows (для колег без Python)

Щоб не пояснювати команднй рядок і `pip install` кожному колезі — можна
зібрати звичайний `OsnastkaMarket-Setup.exe`: подвійний клік, "Далі → Далі →
Готово", ярлик на робочому столі, іконка в треї, автоматичне відкриття
браузера.

**Чесно про обмеження**: PyInstaller (інструмент, що пакує Python-код в
.exe) не вміє збирати Windows-файли на Linux/macOS — це технічне
обмеження самого PyInstaller, не цього проєкту. Тому нижче — два шляхи.

### Спосіб 1 — без Windows-ПК взагалі (рекомендовано)

У поставці вже є `.github/workflows/build-windows-exe.yml` — робочий
процес, який сам збирає `.exe` на справжній Windows-машині в хмарі
GitHub, безкоштовно:

1. Заведи акаунт на github.com (якщо ще нема), створи новий репозиторій
2. Залий туди всі файли з цієї поставки
3. Відкрий вкладку **Actions** в репозиторії — збірка запуститься сама
4. Через ~5 хвилин у розділі **Artifacts** завершеного запуску буде
   `OsnastkaMarket-Setup-installer` — завантаж, розпакуй, роздай колегам
   готовий `OsnastkaMarket-Setup.exe`

Цей workflow навіть сам перевіряє, що зібраний .exe реально запускається
і відповідає на запити, перш ніж пакувати його в інсталятор — тобто
кожна збірка гарантовано робоча, а не "має запуститись".

### Спосіб 2 — на власному Windows-ПК

```
pip install -r requirements.txt
pip install pyinstaller pystray pillow
build_exe.bat
```

Отримаєш `dist\OsnastkaMarket.exe`. Щоб зробити з нього повноцінний
інсталятор (не просто .exe, а Setup з ярликами й деінсталятором) —
встанови безкоштовний [Inno Setup](https://jrsoftware.org/isinfo.php),
відкрий `installer.iss`, натисни Compile (F9). Готовий інсталятор — у
теці `Output\`.

### Як це працює зсередини

- `launcher.py` — тонка обгортка: піднімає CRM через `waitress`
  (production-сервер, працює на Windows на відміну від gunicorn),
  автоматично відкриває браузер, показує іконку в треї з пунктами
  «Відкрити CRM» / «Тека з даними» / «Вийти».
- **Дані (`crm.db`, логи, бекапи) зберігаються НЕ поруч з .exe, а в
  `%LOCALAPPDATA%\OsnastkaMarket`** — постійній домашній теці користувача.
  Це свідоме архітектурне рішення: тимчасова тека, куди PyInstaller
  розпаковує .exe при кожному запуску, видаляється при закритті
  програми — якщо зберігати базу даних туди, вона стиралась би щоразу.
  Заодно це дозволяє встановлювати програму в `Program Files` без
  прав адміністратора на запис у дані.
- Кожен колега, що встановить `OsnastkaMarket-Setup.exe` на свій ПК,
  отримає **власну, окрему** базу даних — це однокористувацький
  десктопний варіант. Якщо потрібна спільна CRM для всієї команди
  одночасно — це сценарій "Запуск у бою" вище (один сервер у мережі,
  усі заходять браузером), а не окремі .exe на кожному ПК.

## Функціональність

### CRM для замовлень на металообробку
Клієнти (з ЄДРПОУ, кількома контактами), воронка угод з 11 стадіями під
реальний цикл замовлення на обробку (лід → технічне завдання/креслення →
КП → переговори → договір → передоплата → виробництво → контроль якості
(ВТК) → відвантаження → закрито), задачі з дедлайнами, календар,
довідник власного обладнання з технічними характеристиками, генерація
комерційної пропозиції в PDF, імпорт/експорт клієнтів в Excel, гнучкі
кастомні поля без правок коду.

### Виробництво (MES-модуль)
Маршрутні карти техпроцесу під кожну категорію обладнання. При переході
угоди на стадію «Передоплата отримана» автоматично створюється
виробниче замовлення з операціями. Алгоритм скінченно-ємнісного
планування розраховує старт/фініш кожної операції з урахуванням
завантаженості робочих центрів, 8-годинного робочого дня та вихідних.
Gantt-схема, ручне позначення виконання операцій.

### Склад
Матеріали/запчастини з мінімальними залишками, партії матеріалу з
номерами плавок і сертифікатами якості (простежуваність), облік ділових
відходів/обрізків для повторного використання, автосписання за нормами
витрат (BOM) при створенні виробничого замовлення, захист від
списання в мінус, автосповіщення про низький залишок.

### Калькулятор вартості
Розрахунок собівартості й ціни виготовлення деталі: матеріал заготовки,
токарна обробка, фрезерна обробка, додаткова обробка (шліфування,
термообробка), наладка на партію, націнка. Контур і габарити для плоских
деталей можна отримати автоматично, завантаживши DXF-креслення — не треба
вимірювати вручну. ШІ-розрахунок вартості вміє аналізувати також фото чи
скан креслення (не лише текстовий опис) і одразу описувати весь
технологічний процес виготовлення.

### Рекламації та доробки
Заявки клієнтів на доробку чи виправлення дефектних деталей, з
пріоритетами, статусами та можливістю прикріпити фото проблеми.

### Аналітика та фінанси
Виручка по місяцях (конвертована в грн), рейтинг менеджерів, причини
програшів, завантаження робочих центрів, глобальна стрічка подій,
окрема сторінка для бухгалтера з усіма платежами по угодах — усе з
урахуванням мультивалютності.

### Багаторівневі права доступу
Сім ролей (адміністратор, продажі, виробництво, склад, сервіс,
бухгалтер, перегляд), розмежування на рівні сервера. Менеджер продажів
бачить лише призначені на нього угоди й клієнтів.

### Інтеграція з реальним обладнанням (Haas)
Верстати Haas із контролером NGC (з 2017–2018) підтримують Ethernet Q
Commands (порт 5051) та MTConnect (порт 8082) без додаткового заліза.
Готові адаптери в `integrations/`:
- `haas_q_adapter.py` — читає `Q301` (Motion Time — сумарне
  напрацювання), `Q300` (Power-On Time), `Q500`/`Q402` (програма,
  статус, лічильник деталей) і шле в CRM.
- `haas_mtconnect_adapter.py` — те саме через MTConnect XML.

```bash
python integrations/haas_q_adapter.py \
    --haas-ip 192.168.1.50 --work-center-id 2 \
    --crm-url http://127.0.0.1:5000 --api-key ВАШ_КЛЮЧ --interval 30
```

API-ключ — на сторінці «Налаштування» в CRM. Перед підключенням до
реального верстата запустіть адаптер із `--debug` і звірте сирі
відповіді контролера — точний формат статусу варто підтвердити на
вашій версії ПЗ Haas.

### Інші інтеграції
Вебхук-сповіщення (Slack-сумісний формат) про аварії обладнання й
низькі залишки складу; курси валют для зведеної звітності.

## Що робити, якщо плануєте зростання

- **PostgreSQL замість SQLite** — коли одночасних користувачів стане
  багато (орієнтовно 15-20+), або якщо потрібен доступ з кількох
  серверів одночасно.
- **Редактор BOM (норм витрат матеріалів) через UI** — зараз норми
  прописані в даних, редагування лише через код.
- **Файлові вкладення** (сканкопії договорів, фото дефектів у сервісних
  заявках) — зараз CRM працює тільки з текстовими даними.
- **Двофакторна автентифікація** для адміністраторів.

## Нові розділи (останнє оновлення)

- **Каталог деталей** (`/parts`) — креслення, матеріал, техпроцес, остання ціна, створення угоди одним кліком.
- **План / факт** (`/production/costs`) — години, матеріали, маржа; вартість машино-години задає адміністратор.
- **Дошка завантаження** (`/production/board`) — 14 днів, перетягування операцій.
- **Контроль якості** (`/quality`) — чек-лист, облік браку, сповіщення.
- **Заявка на закупівлю** (`/warehouse/purchase`) — Excel / Telegram.
- **Прострочені оплати** (`/payments/overdue`), рахунок і акт PDF (`/deals/<id>/invoice.pdf`, `act.pdf`).
- **Повторні замовлення** (`/clients/reorder`).
- **Журнал змін** (`/audit`, лише адміністратор).
- Курси валют з історією, PLN, автооновлення НБУ; щоденні резервні копії; підключення верстатів Haas (MTConnect).
